# Новая архитектура проекта

## 1. Назначение

Система анализирует видеопоток с одной локально подключённой камеры, обнаруживает объекты и опасные события, сохраняет каждое событие одновременно в PostgreSQL и Qdrant, а затем выбирает способ поиска в зависимости от смысла пользовательского запроса.

Целевой контур — локальный или внутренний сервер без публичного доступа к камере и данным.

## 2. Общая схема

```text
Локальная USB-камера
        ↓
camera-ingest
        ↓
YOLO + ByteTrack
        ↓
vision-worker
        ↓
Описание события + LaBSE embedding
        ↓
risk-worker / DangerMLP
        ↓
Event Service
      ↙       ↘
PostgreSQL   Qdrant
      ↘       ↙
   Query Router
        ↓
      FastAPI
        ↓
      Web UI
```

## 2.1. Безопасный поиск (Этап 5)

```text
web → POST /api/query → Redis Stream → query-worker на Mac
                                      ├─ Ollama: только JSON intent и итог по evidence
                                      ├─ LaBSE → Qdrant: общие смысловые запросы
                                      └─ PostgreSQL reader: точные агрегаты
                         Redis result key → FastAPI → web
```

`query-worker` не открывает HTTP-порт. FastAPI не загружает LaBSE или Ollama и ждёт результат в Redis не более 60 секунд. Сообщение подтверждается в consumer group только после записи результата; зависшее сообщение worker забирает через `XAUTOCLAIM`.

LLM не получает SQL и не создаёт его. Он может вернуть только JSON с маршрутом, allowlist-операцией и валидированными фильтрами. Для аналитики разрешены только `count_events`, `list_events`, `group_by_hour`, `group_by_object_type`; период обязателен, ограничен 31 сутками и интерпретируется в `Europe/Moscow`, затем переводится в UTC. Выполняются только заранее определённые параметризованные `SELECT` из view `analytics_events`.

`surveillance_reader` имеет только `SELECT` на view без JPEG/crop. Основной write-пользователь API пишет аудит: SHA-256 нормализованного вопроса, маршрут, безопасные фильтры, итог, latency и число результатов — исходный текст в PostgreSQL не сохраняется.

Qdrant получает фильтры камеры, COCO-типа объекта, риска и времени до top-k. Его результаты всегда повторно загружаются из PostgreSQL; отсутствующие точки пропускаются. Итоговая LLM-цитата принимается только если её `event_id` присутствует в evidence, иначе сервер выдаёт детерминированное резюме.

## 3. Источник видеоданных

Используется одна камера, подключённая непосредственно к компьютеру по USB или доступная как локальное устройство, например `/dev/video0`.

Поддержка нескольких IP-камер и видеорегистратора не является обязательной частью новой архитектуры.

`camera-ingest` отвечает за:

- чтение видеопотока;
- публикацию статуса камеры без автоматического переподключения;
- запуск YOLO;
- передачу обнаружений в ByteTrack;
- формирование единого события с `event_id`;
- выделение полного кадра и crop обнаруженного объекта.

Реализация находится в `src/surveillance/camera/`. Процесс запускается отдельно от API командой:

```bash
PYTHONPATH=src python -m surveillance.camera
```

Он является единственным владельцем локальной камеры, публикует JPEG-preview и статус в Redis, сохраняет события в PostgreSQL и создаёт outbox-запись для последующей индексации в Qdrant. Запись видео, расчёт FPS и автоматическое переподключение камеры не используются.

Если чтение кадра завершается ошибкой, `camera-ingest` освобождает устройство, записывает статус `offline` в Redis и завершает работу. После подключения или замены камеры оператор запускает процесс вручную.

## 4. Анализ события

Для каждого обнаружения создаётся событие, содержащее:

- идентификатор события;
- время в UTC;
- идентификатор локальной камеры;
- track ID;
- тип объекта;
- bounding box;
- confidence;
- полный кадр обнаружения;
- crop объекта.

`vision-worker` формирует текстовое описание события. Описание преобразуется моделью LaBSE в embedding.

`risk-worker` запускает самописную модель `DangerMLP`, которая определяет уровень риска:

- `low`;
- `medium`;
- `high`.

Результат модели является рекомендацией для оператора и не считается подтверждённым инцидентом до ручной проверки.

## 5. Двойное хранение

Каждое событие записывается в две базы данных с одним и тем же `event_id`.

### PostgreSQL

PostgreSQL является источником структурированных данных и хранит:

- `event_id`;
- время события;
- камеру;
- track ID;
- тип объекта;
- confidence;
- bounding box;
- описание;
- уровень риска и вероятности;
- статус подтверждения оператором;
- версию моделей;
- полный кадр в формате JPEG в поле `BYTEA`;
- crop объекта в формате JPEG;
- тип и размеры изображения.

Минимальная структура таблицы:

```sql
CREATE TABLE events (
    event_id UUID PRIMARY KEY,
    camera_id VARCHAR(100) NOT NULL,
    track_id VARCHAR(100),
    occurred_at TIMESTAMPTZ NOT NULL,
    object_type VARCHAR(100),
    confidence DOUBLE PRECISION,
    bbox JSONB,
    description TEXT,
    risk_level VARCHAR(20),
    risk_probability JSONB,
    frame_data BYTEA NOT NULL,
    object_crop BYTEA,
    frame_media_type VARCHAR(50) DEFAULT 'image/jpeg',
    model_version VARCHAR(100),
    alert_status VARCHAR(20) DEFAULT 'pending',
    created_at TIMESTAMPTZ DEFAULT now()
);
```

### Qdrant

Qdrant используется для семантического поиска и хранит:

- embedding описания;
- `event_id`;
- текст события;
- время;
- тип объекта;
- уровень риска;
- идентификатор камеры;
- версии моделей.

Бинарные кадры в Qdrant не дублируются. После получения результатов поиска система использует `event_id` и загружает кадр из PostgreSQL.

## 6. Маршрутизация запросов

Перед поиском запрос передаётся в `Query Router`, который определяет его тип.

### Векторный поиск

Используется для общих и смысловых вопросов:

- «Случалось ли что-то подозрительное в последнее время?»
- «Найди похожие опасные события».
- «Были ли случаи агрессивного поведения?»

Алгоритм:

1. запрос преобразуется в embedding;
2. выполняется поиск в Qdrant;
3. по `event_id` загружаются полные записи и кадры из PostgreSQL;
4. модель формирует ответ с указанием событий, времени и камеры.

### SQL-поиск

Используется для точных вопросов:

- «Сколько машин проехало за последние 3 часа?»
- «Сколько событий высокого риска было вчера?»
- «Когда последний раз обнаруживался автомобиль?»

Алгоритм:

1. Query Router определяет разрешённую операцию и параметры;
2. приложение формирует безопасный SQL-запрос;
3. запрос выполняется в PostgreSQL;
4. результат передаётся модели для формирования понятного ответа.

Используется allowlist аналитических операций; модели запрещено свободно писать SQL:

- `count_events`;
- `list_events`;
- `group_by_hour`;
- `group_by_object_type`;

Для однозначных русскоязычных формулировок («сколько», «покажи», «по часам», «по типам», «сегодня», «вчера», «последние N часов») сервер сам строит валидированный intent. Это защищает поиск от неполного JSON, который может вернуть LLM. Для остальных запросов Qwen возвращает только ограниченный JSON intent или evidence-grounded summary.

## 7. Безопасность SQL

SQL-слой должен:

- разрешать только `SELECT`;
- использовать отдельного пользователя PostgreSQL только с правом чтения;
- обращаться только к view `analytics_events` без JPEG/crop и служебных полей;
- использовать заранее описанные SQLAlchemy Core-запросы с bind-параметрами, а не принимать SQL-строку;
- ограничивать время выполнения и размер результата;
- добавлять обязательные временные ограничения;
- журналировать вопрос, сформированный запрос и результат;
- запрашивать уточнение при неоднозначном вопросе.

## 8. Очередь и надёжность

Redis используется как очередь между компонентами:

```text
camera-ingest → vision-worker → risk-worker → event-service
```

Для записи в две базы применяется единый `event_id`, повторные операции должны быть идемпотентными. Если запись в одну базу не удалась, событие помещается в очередь повторной обработки.

## 9. Web-интерфейс на JavaScript

Web-интерфейс является отдельным статическим клиентом и не содержит логики доступа к камере, PostgreSQL или Qdrant. Он обращается только к FastAPI по HTTP API.

Целевая папка клиента — `web/`:

```text
web/
├── index.html          # Точка входа и базовая разметка
├── assets/
│   ├── styles/         # CSS-файлы
│   └── icons/          # Локальные иконки при необходимости
└── src/
    ├── main.js         # Инициализация приложения
    ├── api.js          # HTTP-клиент FastAPI
    ├── camera.js       # Отображение потока локальной камеры
    ├── search.js       # Естественно-языковой поиск
    ├── events.js       # Лента и карточки событий
    └── alerts.js       # Подтверждение или отклонение тревоги
```

Клиент получает поток камеры, выводит результаты поиска и карточки событий. Он не формирует SQL, не подключается к базам напрямую и не хранит секреты.

## 10. Пользовательский интерфейс

UI содержит:

- просмотр локального видеопотока;
- список последних событий;
- строку семантического поиска;
- ответы по количественным и временным запросам;
- карточку события;
- кадр и crop объекта;
- уровень риска;
- действия `confirm` и `reject`;

Фильтры не являются основным способом работы пользователя. Система должна понимать естественный язык и сама выбирать Qdrant или PostgreSQL.

## 11. Принцип выбора хранилища

```text
Общий смысловой вопрос → Qdrant → PostgreSQL для деталей и кадра

Точное число, дата или период → PostgreSQL → текстовый ответ
```

Обе базы являются частью одного контура данных, а `event_id` используется как ключ связи между векторным и структурированным представлением события.

## 12. Принятые решения реализации

### 12.1. Событие и защита от повторов

- YOLO26n выполняет детекцию на Mac через MPS, ByteTrack остаётся источником исходного `track_id`.
- Адаптер стабильности не заменяет ByteTrack: он сохраняет ID объекта, если тот исчез из кадра менее чем на 15 кадров и повторно появился с достаточным IoU. После превышения этого лимита создаётся новый жизненный цикл трека.
- Событие создаётся только после минимального возраста устойчивого трека. `deduplication_key` включает камеру, стабильный track ID, класс и момент первого появления; Redis presence guard и уникальный индекс PostgreSQL исключают повторные записи одного жизненного цикла.
- Кадр и crop сохраняются в PostgreSQL только для созданного события. Preview с bounding box, классом, confidence и track ID публикуется в Redis в JPEG и не является видеозаписью.

### 12.2. Очереди, workers и ограничение ресурсов Mac

```text
PostgreSQL events + event_outbox
  ├─ vision  → MLX Qwen2.5-VL-3B-Instruct-4bit → vision_analyses
  ├─ risk    → LaBSE + DangerMLP               → risk_assessments / operator_tasks
  └─ qdrant  → LaBSE                            → Qdrant upsert
```

- Vision backend по умолчанию — локальный `mlx-community/Qwen2.5-VL-3B-Instruct-4bit`; Ollama `qwen2.5vl:7b` остаётся совместимым backend для vision и Query Router. Vision prompt запрашивает только русское описание наблюдаемых фактов: без идентификации людей, мотивов и заявления о подтверждённом инциденте.
- `vision`, `risk`, `qdrant` и `query` запускаются host-only на Mac. PostgreSQL, Redis, Qdrant, API и static web запускаются через Docker Compose.
- Тяжёлые операции Qwen и LaBSE координируются Redis lock, concurrency = 1. LaBSE работает на CPU; YOLO использует MPS. Это снижает конкуренцию за unified memory Mac с 16 ГБ ОЗУ.
- Outbox имеет `pending → processing → completed|dead`, максимум три попытки, backoff 2/4 секунды и восстановление зависших задач старше пяти минут. PostgreSQL остаётся источником истины.
- Qdrant хранит только 768-мерный LaBSE embedding и payload. Point ID строго равен `event_id` PostgreSQL; повторный upsert обновляет точку и не создаёт дубликат. JPEG/crop в Qdrant не передаются.

### 12.3. Доступ, ручные решения и аудит

- Роли: `viewer` видит метаданные и поиск; `operator` дополнительно видит preview, кадры/crop и очередь; `supervisor` дополнительно управляет жизненным циклом модельного выпуска.
- Авторизация использует локальные аккаунты, scrypt-хэш пароля и HTTP-only session cookie. Сессия действует не более четырёх часов и завершается после 15 минут неактивности.
- `high` означает только «требует проверки». Он создаёт operator task и не является подтверждённым инцидентом, не запускает внешнее действие и не создаёт автоматическое уведомление.
- `confirm`, `reject` и shadow label выполняются только для pending-задачи в транзакции. Каждое действие пишет append-only запись с оператором, временем, комментарием, предыдущим и новым состоянием.
- Кадры, crop и live-preview доступны только ролям `operator` и `supervisor`; URL медиа выдаются исключительно FastAPI.

### 12.4. Надёжный Query Router

- FastAPI публикует `{request}` в Redis Stream и ожидает ограниченное время. `query-worker` подтверждает сообщение только после сохранения результата с TTL 120 секунд; `XAUTOCLAIM` подбирает брошенные сообщения.
- Смысловой запрос: LaBSE → Qdrant top-k с фильтрами → hydration фактов из PostgreSQL по UUID → краткое evidence-grounded резюме. Если Qwen приводит неизвестный `event_id`, используется детерминированный ответ.
- Количественный запрос: только read-only роль `surveillance_reader`, `analytics_events`, `READ ONLY` транзакция, `statement_timeout=3000ms`, максимум 31 день и лимиты ответа. Нет fallback к write-подключению.
- Каждый запрос пишется в `query_audit_log` как SHA-256 нормализованного текста, маршрут, разрешённая операция, фильтры, результат, latency и error code. Исходный текст пользователя в аудите не хранится.

## 13. DangerMLP: данные, архитектура и метрики

### Назначение и границы

`DangerMLP` — самописный классификатор приоритета текстового описания события. Он не распознаёт личности, не доказывает факт инцидента и не принимает автономных охранных решений. На вход он получает русскоязычное описание от vision-worker, а на выходе даёт вероятности `low`, `medium`, `high` и рекомендуемый класс с максимальной вероятностью.

Текущий локальный выпуск: `danger-mlp-uca-v2`, SHA-256 `da831e252741a4c010f790c5eb2f2fa0f12f96ece38726dbd2f554eb55eda9da`. Веса лежат вне Git в защищённом локальном model registry. При запуске risk-worker проверяет checksum, порядок меток, manifest и model card. Локальная опция запуска draft-весов не снимает ограничение shadow-only.

### Датасет и воспроизводимость

- Первичный источник — UCA (UCF-Crime Annotation), официальный репозиторий на commit `e478cb5b2277c6b7cf6a1dc4691021592003e216`.
- Исходные английские sentence-level аннотации переведены локально моделью OPUS EN→RU; внешние API не использовались. В Git не хранятся исходный набор, переведённые строки или веса.
- Разделение выполняется по `source_video` до embedding; один видеоролик не может попасть более чем в один из train/validation/test. Проверка pipeline блокирует обучение при обнаружении leakage.
- После фильтрации и балансировки использована русская выборка: train — 460 описаний (low 151 / medium 162 / high 147), validation — 444 (171 / 109 / 164), test — 488 (180 / 164 / 144).
- Версия policy `uca-risk-mapping-v1`: `normal → low`; `arrest`, `burglary`, `stealing`, `shoplifting`, `vandalism`, `road_accident → medium`; `abuse`, `assault`, `fighting`, `arson`, `explosion`, `robbery`, `shooting → high`.
- Синтетический набор `synthetic-risk-ru-v1` и генератор локального Qwen подготовлены как отдельный train-only augmentation pipeline. Текущий выпуск `danger-mlp-uca-v2` синтетические строки **не использует**; синтетика никогда не участвует в validation/test и approval-метриках.

Лицензия и условия использования UCA должны быть отдельно проверены перед повторным обучением или развёртыванием за пределами локального исследовательского контура.

### Архитектура и обучение

```text
Русское описание
  → frozen LaBSE (CPU, 768-dim, L2-normalized embedding)
  → Linear(768, 256) → ReLU → Dropout(0.20)
  → Linear(256, 64)  → ReLU → Dropout(0.20)
  → Linear(64, 3)    → Softmax
  → [low, medium, high]
```

- Обучается только собственная PyTorch-голова `DangerMLP`; LaBSE заморожена.
- Loss: weighted cross-entropy для компенсации баланса классов; optimizer: AdamW; seed: 42; batch size: 32; лучший checkpoint выбирается по validation macro-F1.
- Обучение было выполнено на Apple Silicon через MPS; embedding готовились на CPU. Выпуск выбран на epoch 8.

| Validation | 444 | 0.7320 | 0.7203 | 0.7944 | 0.8720 | 0.8314 |
| Test, не использован при выборе | 488 | 0.7602 | 0.7557 | 0.6940 | 0.8819 | 0.7768 |

```text
 [  7, 10,127]]
```

Эти метрики измеряют только отфильтрованные и переведённые UCA-описания. Они не являются оценкой качества на живой камере. До утверждения требуются минимум 50 вручную размеченных русских описаний текущей vision-модели, macro-F1 не ниже 0.60, recall класса `high` не ниже 0.75, calibration и решение supervisor. Даже после approval модель остаётся в shadow mode, а `high` создаёт только задачу оператору.

## 14. Эксплуатационные границы

- Контур рассчитан на локальный Mac или внутренний сервер; внешнего публичного доступа к камере, PostgreSQL, Redis и Qdrant нет.
- Видеофайлы на диск не записываются, FPS не вычисляется и не показывается.
- При остановке Compose или host-workers данные PostgreSQL/Qdrant не удаляются. Безопасный rollback переключает версию worker/model и не удаляет исторические события.
- Production-инфраструктура (внутренний Nginx/TLS, backup PostgreSQL/Qdrant, CI secret/SAST/dependency scans) остаётся следующим этапом и не считается включённой локальной конфигурацией.
