# Архитектура проекта

Статус: документированное состояние на 2026-10-04. Это монолитный Python/Flask PoC системы видеоаналитики для четырёх камер. Ниже факты об имеющемся коде и целевая дисциплина его развития, а не описание гарантированно работающей production-системы.

## Текущий поток данных

```text
4 MJPEG-камеры
  -> по daemon-thread на камеру (app.py)
  -> YOLO `track()` + самописный `UniqueObjectTracker`
  -> crop нового объекта
  -> Ollama/Gemma vision (глобально сериализован через `question_lock`)
  -> SQLite `logs` + append в `logs.md`
  -> раз в >=5 мин.: LaBSE embedding -> Qdrant `surveillance_collection`

Оператор: HTML/JS
  -> `/video_feed` MJPEG
  -> `/search_logs` SQLite-фильтр
  -> `/makejob` -> LaBSE -> Qdrant top-4 -> CrossEncoder -> Mistral через Bothub
```

Сервис дополнительно регистрирует себя через `registr.py` на внешнем HTTP endpoint. Запуск выполняется Waitress на `0.0.0.0:8090`.

## Границы компонентов

| Компонент | Ответственность | Текущее состояние |
|---|---|---|
| `app.py` | API, ingest камер, inference, хранение, RAG, запуск | Все ответственности смешаны в одном модуле |
| `registr.py` | Определение IP и регистрация сервиса | Внешние адрес и статический UUID захардкожены |
| SQLite | Точный журнал событий | Без миграций, индексов, UTC-политики и retention |
| `logs.md` | Буфер перед векторизацией | Формат записи и формат парсинга несовместимы |
| Qdrant | Векторное retrieval-хранилище | Локальные данные занимают ~131 MB и не должны быть в Git |
| HTML | Видеостена, SQL-поиск, чат | В коде есть несовпадение контрактов API |

## Подтверждённые ошибки и архитектурный долг

### Блокирующие пользовательский путь

1. Чат не работает: UI отправляет `{question}`, `POST /makejob` читает `data["request"]` (`templates/index.html`, `app.py`). API вернёт 400 для нормального запроса.
2. `end_time` в UI использует несуществующую переменную вместо `endTime`; при заполнении окончания периода будет `ReferenceError`.
3. В `logs.md` writer пишет `Timestamp:`, `Camera:`, `Type:`, `ID:`, `**Description**:`, но parser ожидает `**Timestamp**`, `**Camera**`, `**Type**`, `**ID**`, `Описание:`. В результате payload/chunk Qdrant теряет метаданные и описание.
4. API-ключ Bothub пустой в исходнике. Без внешней конфигурации ответ Mistral не будет получен.

### Корректность и производительность

1. Встроенный ByteTrack используется вместе с самописным IoU-трекером; фактические track ID YOLO игнорируются. Самописный ID начинается заново на каждой камере, поэтому `global_tracker` смешивает разные объекты и не используется для результата.
2. В формуле IoU используется `box2Area = w2 * h1` вместо `w2 * h2`, что ломает сопоставление bbox.
3. Vision-вызов выполняется прямо в camera loop; общий lock блокирует LLaVA/Gemma для всех камер. При задержке модели поток камеры перестаёт читать кадры.
4. Thread’ы камер и регистрация запускаются при import модуля, а не через lifecycle приложения. Любой test/import и multi-worker deployment запускает дублирующие подключения и inference.
5. Qdrant upsert создаёт случайные UUID; отсутствует идемпотентный ключ события. Нет фильтра по времени/камере в vector retrieval, а LLM не возвращает ссылки на первичные события.
6. SQLite date хранится как TEXT `YYYY-MM-DD HH:MM:SS`, тогда как HTML datetime-local передаёт `T`; текстовые сравнения start/end_time некорректны.
7. Нет backpressure, таймаутов, retries/DLQ, health checks, метрик, ограничения контекста и пагинации.

### Безопасность и эксплуатация

1. URL камер с токенами, адрес регистрации, UUID и конфигурация сервисов — в исходниках.
2. Нет authentication/authorization/TLS/rate limiting у видеопотока, журналов, поиска и команды переподключения.
3. Логируются все headers и тело пользовательского запроса; это может раскрывать секреты и персональные данные.
4. RAG-контекст и prompt содержат недостоверные демонстрационные события. Они могут заставлять модель сообщать несуществующие инциденты.
5. `qdrant_data/` и runtime-артефакты попали в рабочее дерево Git. Их нельзя коммитить или редактировать вручную.

## Целевая эволюция

Разделить монолит на четыре независимо тестируемые зоны:

```text
API (auth, contracts, UI) -> PostgreSQL/event repository <- worker queue
                                            ^                  |
camera ingest -> detector + единственный tracker -> event builder -> vision worker
                                            |
                                      object storage (frame/clip)

RAG API: SQL metadata filters -> vector top-k -> optional reranker -> LLM with evidence IDs
```

### Двухконтурная оценка риска

После появления события vision worker запускает параллельно два независимых сигнала: Ollama оценивает непосредственно кадр, а `DangerMLP` оценивает текстовое описание через LaBSE. Fusion слой хранит оба score и причину. Совпадение `high` даёт pending alert; одиночный `high` с вероятностью >= 0.85 также создаёт pending alert, но всегда с пометкой о расхождении. Автоматических действий нет.

До такой миграции не добавлять новые бизнес-функции в `app.py`: сначала выделить конфигурацию, repositories, `camera_worker`, `vision_worker` и API schemas. SQL — источник точных фактов; Qdrant — только поиск кандидатов. Ответ ассистента обязан содержать ID события, камеру и время либо явное «данных нет».

## Инварианты данных

- Время хранится в UTC, машинно (epoch или RFC 3339), UI конвертирует только для отображения.
- `event_id` — стабильный UUID; `track_id` имеет namespace камеры/сессии и не является идентификатором личности.
- Каждое RAG-событие имеет первичный источник: camera_id, timestamp, frame/clip URI и версию модели.
- Идемпотентность ingestion: повторный запуск не создаёт дубликат того же события.
- Модель не устанавливает факт нарушения/личность; она возвращает наблюдение и confidence/статус.

## Этап 6: доступ и ручная проверка

Все API, кроме health и login/logout, требуют локальную session-cookie. `viewer` видит только метаданные; `operator` и `supervisor` получают доступ к preview, JPEG-кадрам и crop. Сессия действует 4 часа и истекает после 15 минут простоя.

High-оценка DangerMLP формирует только shadow-задачу. Confirm/reject сохраняют пользователя, время, комментарий и состояние в неизменяемом `operator_decision_audit`; они не означают подтверждённый инцидент и не запускают внешнее действие.

Risk-worker допускает только один approved release, совпадающий по checksum, версии mapping и threshold policy с локальными весами. Approval требует минимум 50 ручных русскоязычных примеров, macro-F1 не ниже 0.60 и recall high не ниже 0.75. Текущий checkpoint этим критериям не соответствует.
